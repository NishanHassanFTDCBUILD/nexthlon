# Nexthlon product development plan

**Release objective.** A shopper can track a purchase, resolve an order problem, understand their wallet and control their account from a phone. A staff member can find the same order, see what the customer sees, take an authorized action and verify the outcome. These two journeys set the standard for the rest of the product.

**Scope and evidence.** This plan covers the full account and admin surfaces plus their dependencies on checkout, fulfilment and payments. “Existing” means represented in the current repository. Production readiness requires staging and deployment evidence. Amazon is a benchmark for self-service, predictability and operating discipline. Capacity figures below are proposed test targets.

## 2. Build a complete customer profile

Make **My account** the front door. The first screen answers “Where is my order?” and “Do I need to do anything?” Show the latest active order, one time-sensitive action when applicable, then shortcuts to orders, wallet, addresses and help. For a first-time shopper, show useful setup actions and the route back to shopping. Preserve existing bookmarks, including the legacy profile and order links.

## 4. Design direction — Obsidian & Volt

Keep the sports-shop identity recognizable. Use matte graphite surfaces, warm white text, existing typography and a restrained volt accent for the primary action or active step. Let a crisp product image, size and order status identify a purchase at a glance. Reserve red for destructive actions and pair every status color with text or an icon.

- **Customer order detail:** Lead with “Arrives Thursday” or “Delivered,” followed by the item photo, purchased size and tracking. Place invoice, help and eligible after-sales actions below. A cancellation sheet shows the amount, wallet destination and two clearly separated buttons. Return focus to the initiating control on close.
- **Staff order detail:** Use the same item grouping and timeline. On wide screens put permitted actions and their consequences beside the record. On phones use a single column with an action sheet. Keep the order number and status visible while moving between items, payment and history.
- **Interaction system:** Build shared patterns for money, timestamps, status, filters, list rows, confirmation, inline errors and pending operations. Keep filled forms after errors. Announce saves to screen readers. Use a quiet success state when reduced motion is enabled.
- **Design review:** Prototype account home, order detail, cancellation, dispatch and reconciliation first. Test at 320, 390, 768 and 1440 pixels, at 200% zoom and with keyboard-only navigation. Require readable long IDs, visible focus, meaningful empty states, accessible labels and 44px touch targets. Keep animation off the critical path for staff tasks.
- **Usability gate:** Give five shoppers and three staff testers realistic tasks without coaching. Record task completion, wrong turns and time. Revise any flow that causes a money or shipment mistake. Repeat the same task before approving the design.

## 5. Architecture and scaling path

**First release.** Keep Express/EJS and MongoDB as a modular monolith. Separate web traffic and background work at deployment. Give each business domain a service owner in code. Both account and admin controllers call the same business rules and read the same order projection. Maintain existing URLs and API responses while migrating each screen.

| Boundary                      | Authoritative data and rules                                                                                                                        | Scaling or failure strategy                                                                                                                                                                                   |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identity and customer account | User, addresses, sessions and preferences. Enforce owner scope and staff permissions on the server. Keep customer and admin JWT audiences separate. | Private responses bypass shared caches. Share rate limits between web instances. Test session renewal across instances.                                                                                       |
| Catalog and discovery         | Product, category, offer and variant identity. Price and availability are rechecked at purchase.                                                    | Put public assets and eligible guest pages behind a CDN. Use shared cache invalidation after updates. Add a search index when indexed MongoDB queries miss the latency target.                                |
| Order and fulfilment          | One order lifecycle, item-level states, shipment references and permitted transitions.                                                              | Use conditional updates and version checks. Index queues by state and age, paginate stably, and monitor query plans against production-sized fixtures.                                                        |
| Inventory and money           | Stock receipts, order totals in integer paise, wallet entries, payment attempts and settlement references.                                          | Use MongoDB replica-set transactions where records must agree. Persist idempotency keys with the mutation. A repeated request returns the original outcome. Provider calls run outside database transactions. |
| Events and integrations       | Durable intent to send email, book shipping, publish order updates or reconcile payments.                                                           | Extend the existing jobs system with a transactional outbox for critical transitions. Workers claim leased jobs, deduplicate delivery, back off on failure and surface exhausted retries to operators.        |
| Reporting and operations      | Derived sales, refund, support and stock metrics, each with a defined owner and freshness timestamp.                                                | Move expensive reports and exports to workers. Build reporting projections before considering a separate analytics store. Keep request IDs, order IDs and job IDs traceable without logging credentials.      |

**Reference journey.** On an eligible cancellation, the order service checks ownership, item state and amount. It records the cancellation, stock release, wallet entitlement and event intent consistently. The customer sees processing until credit is posted. A worker delivers the notification. If a response is lost or the worker restarts, the same cancellation reference produces one credit and one stock release. The finance view exposes any unsettled amount until reconciliation completes.

**Capacity decisions.** Establish a production-like staging baseline with realistic order history, variants and concurrent workers. Measure browsing, account reads, writes and queue lag separately. Test a sale scenario with 90% public browsing, 8% authenticated reads and 2% writes as an initial assumption, then replace the mix with observed traffic. Increase load until a target fails and report the sustained request rate, hardware, cache hit rate, errors and database connections. Treat the existing 50,000-visitor ambition separately from simultaneous checkout writes. Add web replicas for sustained web saturation, worker capacity for queue backlog and indexes or projections for slow queries. Extract a service only when measurements identify an independent bottleneck or operational owner.

## 6. Delivery order and release decisions

Estimates assume one full-time developer and part-time design and QA support. Re-estimate after the first staging pass. Each phase ends in a usable release candidate.

| Phase                                 | Window    | Deliverable and owner                                                                                                                                                        | Exit evidence                                                                                                                                         |
| ------------------------------------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0 — Establish trust                  | Week 1    | Engineering and QA inventory the current flows, configure staging replica set, worker, isolated provider test accounts and fixtures. Measure the current UX and API timings. | Run database suites, legacy owner login, payment replay, stock contention and backup restore. Record pass/fail and assign every blocker.              |
| P1 — Customer self-service            | Weeks 2–3 | Design and engineering deliver account home, identity, addresses, order detail, tracking, help and wallet cancellation as one end-to-end journey.                            | A shopper completes the core tasks on mobile and desktop. An eligible cancellation yields exactly one credit, and staff see the same result.          |
| P2 — Staff operations                 | Weeks 4–5 | Engineering and a store operator ship dispatch ownership, queue ageing, bulk previews, finance exceptions and linked support cases.                                          | Two staff process concurrent updates without double dispatch or duplicate credit. Reports agree with drilldowns.                                      |
| P3 — Complete the profile and catalog | Weeks 6–7 | Engineering and merchandising add fit preferences, saved-shopping improvements, notification history, product quality checks and promotion previews.                         | Test empty and established accounts, unavailable variants, opt-outs and overlapping promotions. All controls have loading, error and recovery states. |
| P4 — Launch rehearsal                 | Week 8    | Engineering and operations run peak-load, worker-restart, provider-timeout and restore drills. Roll out by staff role and a small customer cohort using feature flags.       | Sign off on measured performance, accessibility, recovery and business reconciliation. Expand rollout only after reviewing the first cohort.          |

**If shipping a hackathon demo first:** Deliver P0 and one complete P1/P2 slice. Demonstrate a shopper tracking an order, cancelling one eligible item, seeing wallet credit and using it on another purchase. Switch to staff to show the matching history, stock change and dispatch queue. Use seeded data and provider test mode. This demonstrates the architecture through a transaction the audience can follow.

## 7. Measures and go-live gates

| Measure                       | Proposed acceptance target                                                                                                                            | How to verify                                                                                                                                               |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Customer task success         | At least 90% unassisted completion for tracking, finding an invoice and checking cancellation credit in a broader pilot                               | Count completed tasks divided by attempts, report sample size, and compare with the P0 baseline.                                                            |
| Staff efficiency              | Reduce median time from opening a dispatch queue to completing an eligible order by 25%                                                               | Time the same representative orders before and after. Track skipped and incorrect actions alongside speed.                                                  |
| Financial and stock integrity | Zero duplicate credits, duplicate stock releases or unexplained balance differences in the release scenarios                                          | Reconcile orders, receipts and ledger entries after retries, concurrent edits and injected process failures.                                                |
| Responsiveness                | Target mobile p75 LCP ≤2.5s, INP ≤200ms and CLS ≤0.1. Target p95 account reads ≤500ms under the agreed pilot load.                                    | Measure on representative phones and staging hardware. Record cache state, data volume and traffic mix.                                                     |
| Operations                    | Proposed launch service objective of 99.9% monthly availability. Proposed recovery targets of 15 minutes of data loss and 2 hours to restore service. | Assign an alert owner, measure real availability after launch, and time a restore drill against the targets before promising them.                          |
| Release safety                | No unresolved critical permission, money, stock or data-loss defects                                                                                  | Verify account isolation, role matrix, checkout callbacks, worker recovery and private cache behavior. Roll back UI flags independently of data migrations. |

Use additive schema changes first, backfill in bounded batches, and read both data shapes until verification is complete. On a release regression, disable the affected write path, preserve its receipts and reconcile pending work before reopening it. Preserve historical payment and order records throughout rollout.
